# Porting guide: how a WarpLib function becomes Rust

This document is the checklist every ported function must satisfy. It is written for humans
and for coding agents alike: follow it literally and `cargo xtask dev-check` stays green.

## 1. Sources of truth

- The Java reference is a read-only sparse checkout under `reference/warp10/` (git-ignored,
  revision `b5764364679f6ccc40a23632e352d134fab1c2eb`). The registry is
  `reference/warp10/warp10/src/main/java/io/warp10/script/WarpScriptLib.java`; functions
  live in `reference/warp10/warp10/src/main/java/io/warp10/script/functions/` (one class per
  function, sometimes shared: `NumericalUnaryFunction`, `DIGEST`, `SNAPSHOT`…).
- `docs/warplib-inventory.tsv` lists every registered name with its Java class;
  `docs/FUNCTIONS.md` (generated by `cargo xtask functions`) shows what is ported.
- **Read the Java before writing Rust.** Semantics, operand order, type checks, the exact
  error messages and the corner cases (empty input, `null`, `NaN`, `-0.0`, `Long.MIN_VALUE`,
  index out of range, negative counts…) all come from the Java source.
- When a Java library result is needed (`java.lang.Math`, `java.util.Random`, `Double.toString`,
  Commons Math, Joda-Time, BouncyCastle, `String.format`…), **generate the reference value
  with Java**: a JDK is installed (`java`, `javac`). Keep scratch programs under `/tmp/jref/`
  (Commons Math 3.6.1: `/tmp/jref/commons-math3.jar`; BouncyCastle 1.78.1:
  `/tmp/jref/bc/bcprov-jdk18on-1.78.1.jar`; Joda-Time 2.13.1:
  `/tmp/jref/joda/joda-time-2.13.1.jar` — fetch them again from Maven Central when `/tmp` was
  cleaned). Embed the generated values in the test files as literals. Never guess a floating
  point digit.
- Java semantics that scripts can observe but that are not WarpScript-level (JDK exception
  texts such as `Index 0 out of bounds for length 0`, `Value 13 for monthOfYear must be in the
  range [1,12]`, `d != java.lang.Double`) are reproduced verbatim: they are what a Warp 10 user
  sees in the error message.
- When a whole-script result is needed (the interplay of several functions, a stack state
  after an error, the exact JSON of a `FETCH`…), a real Warp 10 can serve as the oracle: the
  official image `warp10io/warp10:3.5.0-alpine` (there is no `latest` tag) runs under
  `podman run -d --name w10 -p 18080:8080 docker.io/warp10io/warp10:3.5.0-alpine` (about 40 s
  to start) and answers `curl --data-binary 'script' http://127.0.0.1:18080/api/v0/exec`: the
  response is the stack as a JSON array, **top of the stack first**; errors come in the
  `X-Warp10-Error-Message` header. `port_helpers/w10.sh 'script'` (recreate it under the
  git-ignored `port_helpers/`, see §6) wraps that. The image runs JDK 8, whose exception texts (`-1`, `java.lang.String cannot
  be cast to java.lang.Number`) differ from the JDK 11+ texts the port reproduces. Use it to
  settle a doubt, then embed the observed values in the tests as literals. Since `BUCKETIZE`
  is available on both sides, bucketized series can be built on the oracle with
  `[ gts bucketizer.sum 100 10 0 ] BUCKETIZE 0 GET` and in Rust tests with
  `GeoTimeSerie::with_buckets`. The image's fat jar (`podman cp
  w10:/opt/warp10/bin/warp10-3.5.0.jar port_helpers/ref/`) also runs Warp 10's own classes on the
  local JDK (a scratch `main` calling e.g. `DTW.compute` or `PolynomialCurveFitter`): use it
  when the JDK 8 answer of the oracle differs from JDK 11+ (`Math.toRadians`, exception
  texts). The oracle runs 3.5.0 while the reference sources are a later `master`: when they
  disagree (a bug fixed since), the port follows the sources and the test overrides the
  oracle's answer.
- Geo Time Series internals (`GeoTimeSerie`, `GTSHelper`, `GTSEncoder`/`GTSDecoder`) are
  under `reference/warp10/warp10/src/main/java/io/warp10/continuum/gts/`; the GeoXP point
  conversions come from GeoXP Lib (`reference/geoxplib/`, Apache-2.0, see `NOTICE`).

## 2. Where the code goes

```
crates/warpscript/src/
  value.rs            Value enum (reference semantics for LIST / MAP / SET, Java equals/hashCode)
  stack.rs            Stack: push/pop/peek/popn, symbols, registers, attributes, config, macros
  error.rs            Error::new(msg) ; messages are wrapped by the interpreter with the position
  format.rs           Java number formatting / parsing (Double.toString, Long.parseLong…)
  jmath.rs            exact java.lang.Math ports
  gts.rs              GeoTimeSerie / Metadata model (GTSHelper primitives: setValue, sort, valueSort,
                      subserie, select…); geoxp.rs: HHCode conversions (GeoXP Lib)
  aggregators/        WarpScriptAggregatorFunction objects (bucketizer.*, mapper.*, reducer.*):
                      mod.rs (Aggregator trait, AggregatorArgs, Named wrapper), basic.rs…
  functions/
    gts.rs            GTS construction / inspection; gts_time.rs, gts_points.rs, gts_stats.rs:
                      GTSHelper transforms; gts_frameworks.rs: BUCKETIZE (MAP / REDUCE to come)
    mod.rs            TABLES (registration order) + `mod xxx_tests;` declarations
    args.rs           pop_string / pop_long / pop_list / pop_map / pop_number / getn / fail
    <group>.rs        one module per function family, `pub const FUNCTIONS: &[(&str, Entry)]`
    <group>_tests.rs  its unit tests (excluded from coverage)
```

A new group is added to `TABLES` in `functions/mod.rs` and its test module is declared there
(`#[cfg(test)] mod <group>_tests;`). Names must be unique across all tables.

## 3. Implementation rules

1. **Behaviour first.** Same operand order, same result types (`LONG` vs `DOUBLE`), same
   reference-vs-copy semantics as Java (a function that mutates its input in Java mutates it
   here; one that builds a new list builds a new list here), same iteration order
   (`LinkedHashMap` / `LinkedHashSet` → `IndexMap` / `IndexSet`).
2. **Error messages verbatim.** Use `fail("NAME", "message")` → `"NAME message"`, exactly the
   Java `getName() + " message"` text, including trailing periods. Type errors raised by Java
   as `ClassCastException` / `NullPointerException` get a descriptive `NAME …` message and a
   note in `docs/DIVERGENCES.md` only when a script could observe the difference.
3. **Never panic** in library code: `clippy::unwrap_used`, `expect_used`, `panic`,
   `unreachable` (and `indexing_slicing` style accesses on untrusted indices) are denied.
   Validate, then use `get`, `checked_*`, `wrapping_*`, `unwrap_or`.
4. **Clippy pedantic is on and warnings are errors.** Typical fixes: `#[allow(clippy::float_cmp)]`
   on functions that compare floats on purpose, avoid `many_single_char_names`, no
   `needless_pass_by_value`, document every public item (`missing_docs`).
5. **Java integer semantics.** `long` arithmetic wraps (`wrapping_add`…); `(long) double`
   saturates and maps `NaN` to 0 (`value::double_to_long`); `Number.intValue()` keeps the
   low 32 bits (`args::int_value`); string indices are UTF-16 code units in Java — document
   when a function is index-based and strings may hold non-BMP characters.
6. **No new dependency without a reason.** Workspace dependencies are declared in the root
   `Cargo.toml` (`[workspace.dependencies]`) and used with `{ workspace = true }`. They must
   pass `cargo deny` (license allow-list in `deny.toml`) and `cargo audit`. Prefer small,
   pure-Rust, well-maintained crates; `std::random` is unstable, use `getrandom`.
7. **Document divergences** in `docs/DIVERGENCES.md` whenever behaviour cannot or should not
   match Java exactly (platform-dependent floating point, JVM-only features, security).

## 4. Tests and the 100 % coverage gate

- Tests live in `<group>_tests.rs`, start with
  `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic)]` and use the helpers of
  `crate::tests`:
  - `assert_top(script, expected)` — runs the script, compares the top of the stack
    (`Value` equality is Java `equals`: `1 != 1.0`, `NaN == NaN`, `0.0 != -0.0`);
  - `assert_stack(script, &[values])`, `assert_fails(script, needle)`, `fail_msg(script)`,
    `exec(script) -> Stack`, `top(script) -> Value`, `run(script) -> Vec<Value>`.
  - To test code paths that no script can reach (API only), call the function through
    `crate::functions::call(&mut stack, "NAME")` or the module's `pub(crate)` helpers.
- **Every region must execute**: each `?`, each `match` arm, each `if`/`else`, each closure,
  including "empty stack" paths (call the function with 0 and 1 operands) and every error
  message. A fallback arm that cannot be reached is dead code: restructure instead of leaving
  it (e.g. return `Option` from a helper and `?` on it).
- Run `cargo xtask coverage`; it fails below 100 % files / lines / regions / functions. To see
  what is missing:
  ```
  cargo llvm-cov report --ignore-filename-regex '(/tests\.rs$|_tests\.rs$|/proofs\.rs$|/tests/|/benches/|/examples/|/xtask/|/target/)' --text -- --show-regions=true > /tmp/cov.txt
  grep -n '\^0' /tmp/cov.txt
  ```
- Optional: pure helpers (no allocation, bounded loops) can get a Kani harness in
  `crates/warpscript/src/proofs.rs`; keep the whole proof step under a few minutes.

## 5. Infrastructure the host provides

Some Java behaviour depends on the server around the stack. The runtime exposes hooks the
host (`crates/influxftl`) fills in; functions must use them rather than hard-code a policy:

- capabilities: `Stack::capabilities_mut()` (token attributes), `Stack::capability(name)`;
  `limits::pop_limit` implements the `MAXOPS`-style `'<cap>' or 'limits'` pattern;
- tokens: `Stack::set_token_resolver` (`CAPADD`);
- interactive output: `Stack::set_interactive_writer` (`PEEK`, `PSTACK`…);
- secure scripts: `Stack::set_secure_codec`; configuration: `Stack::set_config`.

Test stacks (`crate::tests::test_stack`) have unlimited limits and the `limits` capability.

## 6. Long runs

`cargo xtask dev-check` takes about seven minutes (Kani included) and `cargo xtask coverage`
about two. Run them detached from the editor so that closing it never kills the run, e.g.
with the helper kept out of the sources in the git-ignored `port_helpers/bgjob.sh` (not
under `target/`, which `cargo clean` wipes):

```
port_helpers/bgjob.sh run devcheck /path/to/influxftl 'cargo xtask dev-check'
port_helpers/bgjob.sh wait devcheck 700 ; tail -3 /tmp/influxftl-jobs/devcheck.log
```

(`run <name> <dir> '<cmd>'`, `status [name]`, `log <name> [lines]`, `wait <name> [seconds]`;
each job runs as its own `systemd-run --user` transient service with a memory ceiling, so a
runaway build is OOM-killed alone instead of the editor, with a `setsid nohup` fallback
without systemd; it writes `/tmp/influxftl-jobs/<name>.{log,pid,exit}`.)

The oracle wrapper `port_helpers/w10.sh` is a four-liner: `curl -s -D - --data-binary "$1"
http://127.0.0.1:18080/api/v0/exec`, printing the `X-Warp10-Error-Message` header when
present and the body (the JSON stack) otherwise.

Start the oracle containers with `systemd-run --user --unit=influxftl-oracle --remain-after-exit -p
KillMode=none podman start w10 idb3`, not from a `bgjob` run: the job's cgroup is killed when the job
ends, which takes the container's `conmon` and its port forwarding down with it. Warp 10 can take up
to 3 minutes to answer after a start; poll `curl -s -o /dev/null -w '%{http_code}'
http://127.0.0.1:18080/api/v0/plasma` until it prints `200`.

A coverage gap finder, once `cargo llvm-cov report --text -- --show-regions=true > /tmp/cov.txt`
has run: `awk '$0 ~ "/<file>.rs:$" {p=1;next} /^\/home.*\.rs:$/ {p=0} p' /tmp/cov.txt | grep -n
-B6 '\^0\|      0|'`. Note that `if let … else`-less blocks, `?` and closures all create regions:
an unreachable arm or `?` must be restructured away (e.g. carry an `Option` instead of a
variant that cannot occur) rather than left uncovered.

## 7. The gate

```
cargo fmt --all
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test -p warpscript
cargo xtask coverage
cargo xtask functions          # regenerates docs/FUNCTIONS.md
cargo xtask dev-check          # security-audit → check → fmt → clippy → test → coverage → proof
```

Commit locally once `dev-check` is green (one commit per function family). **Never push.**

## 8. Licensing and provenance

The project is Apache-2.0 and must stay redistributable under it (see `README.md` §8 and
`NOTICE`). When porting:

1. **Warp 10 code may be ported** (Apache-2.0). Every new source file starts with the two
   header lines used everywhere:
   ```
   // Copyright 2026 The influxftl Authors. Licensed under the Apache License, Version 2.0.
   // Derived from Warp 10 (Copyright 2018-2026 SenX S.A.S., Apache-2.0), ported to Rust and modified.
   ```
2. **Other Apache-2.0 or MIT/BSD-style libraries Warp 10 delegates to** (mustache.java,
   Commons Math, Joda-Time, Jackson, Guava, Bouncy Castle, fdlibm…) may be ported too. Add a
   `// Derived from …` line naming the work, its copyright holder and license to the file
   header, and add the work to `NOTICE` (reproduce its own `NOTICE` attributions when it has
   one, the full copyright/permission notice for MIT-style licenses). Note the Warp 10
   `NOTICE` credits the FastDTW implementation (Stan Salvador, MIT): restore that paragraph
   in `NOTICE` when `DTW` / `OPTDTW` are ported.
3. **Never transliterate OpenJDK code** (GPLv2 + Classpath exception is not compatible with
   redistribution under Apache-2.0). JDK behaviour (`java.lang.Math`, `java.util.Random`,
   `java.util.Formatter`, `Double.toString`, collections, charsets…) is implemented from the
   published specification (the Javadoc) and from black-box reference values generated with
   `java` (see §1); do not read the JDK sources to write the Rust code. The same applies to any
   GPL, LGPL, AGPL or source-available dependency of Warp 10.
4. **Reference values and error texts are facts, not expression**: embedding JDK outputs,
   exception messages or CLDR symbols in tests and code is fine.
5. New crates must pass `cargo deny` (`deny.toml` allow-list); do not add exceptions for
   copyleft licenses.

## 9. Status and next steps

(`crates/influxftl`): the stack comes back as JSON, top first, with `X-Warp10-Elapsed` /
`X-Warp10-Ops`, and a failing script as a `500` with `X-Warp10-Error-Line` and
`X-Warp10-Error-Message`. The datastore functions (`FETCH`, `FIND`, `FINDSETS`, `FINDSTATS`,
`UPDATE`, `META`, `METADIFF`, `DELETE`; `docs/DATASTORE.md`) work on InfluxDB 3
(`INFLUXFTL_DATASTORE=influxdb3`: `crates/influxftl/src/influx`, a `std` HTTP client, SQL for
reads, line protocol for writes; DIVERGENCES §34) or on a datastore in memory
(`INFLUXFTL_DATASTORE=memory`). It was checked on InfluxDB 3 Core 3.12.

Warp 10 registers through `Builder`s and constants). The Geo Time Series model, the
